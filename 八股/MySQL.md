## MySQL 基础

0. ⋆ 什么是 MySQL？

MySQL 是一个开源的、流行的关系型数据库管理系统 (RDBMS)，它使用结构化查询语言 (SQL) 来管理数据。

1. 两张表怎么进行连接？

使用 JOIN 子句（INNER JOIN, LEFT JOIN, RIGHT JOIN）基于共同的列（通常是外键）进行连接。

**2. 内连接、左连接、右连接有什么区别？**

- **内连接 (INNER JOIN)**：只返回两表中连接字段相**匹配**的行。
- **左连接 (LEFT JOIN)**：返回**左表**的所有行，以及右表中匹配的行。不匹配的右表字段为 `NULL`。
- **右连接 (RIGHT JOIN)**：返回**右表**的所有行，以及左表中匹配的行。不匹配的左表字段为 `NULL`。

**3. 说一下数据库的三大范式？**

- **第一范式 (1NF)**：确保表的**所有列都是原子性的**，不可再分。
- **第二范式 (2NF)**：满足 1NF，并且**非主键列完全依赖于主键**（不能只依赖于主键的一部分）。
- **第三范式 (3NF)**：满足 2NF，并且**非主键列之间没有传递依赖**（即非主键列不能依赖于另一个非主键列）。

**4. varchar 与 char 的区别？**

- **CHAR**：**定长**存储，存储时总是占用定义的长度，查询速度快，但可能浪费空间。
- **VARCHAR**：**变长**存储，只占用实际字符的长度加 1-2 字节来存储长度，节省空间，但查询速度略慢。
- blob 和 text 有什么区别？

两者都用于存储大量数据。BLOB (Binary Large Object) 存储二进制数据（如图片、文件），TEXT 存储字符数据（如长文本、文章）。它们都有不同的子类型（TINY, SMALL, MEDIUM, LONG）。

**6. DATETIME 和 TIMESTAMP 有什么区别？**

- **DATETIME**：存储固定日期和时间范围（`1000-01-01` 到 `9999-12-31`），**不随时区变化**。占用 8 字节。
- **TIMESTAMP**：存储时间戳范围（`1970-01-01` 到 `2038-01-19`），**与时区相关**，存储时转换为 UTC，取出时转换为当前时区。占用 4 字节。

**7. in 和 exists 的区别？**

- **`IN`**：子查询先执行，适用于**子查询结果集较小**的情况。

- **`EXISTS`**：外层查询先执行，子查询作为判断条件，适用于**外层查询结果集较小**或**子查询结果集较大**的情况。

8. 记录货币用什么类型比较好？

建议使用 DECIMAL 或 NUMERIC 类型。它们用于存储精确的数值，可以指定精度（总位数）和小数位数，避免浮点数（FLOAT/DOUBLE）的精度丢失问题。

9. ⋆ 怎么存储 emoji?

为了存储包括 emoji 在内的所有 Unicode 字符，需要将数据库、表和列的字符集设置为支持 4 字节 Unicode 编码的字符集，即 utf8mb4（utf8 只支持 1-3 字节，无法存储 emoji）。

10. drop、delete 与 truncate 的区别？
| 命令 | 级别 | 是否可回滚 | 影响 |
| :--- | :--- | :--- | :--- |
| **DROP** | **DDL**（数据定义） | 否 | 删除**整个表结构和数据**，释放空间。 |
| **TRUNCATE** | **DDL**（数据定义） | 否 | 删除表中**所有数据**，**保留表结构**，通过释放高水位线快速执行。 |
| **DELETE** | **DML**（数据操作） | 是 | **逐行删除**数据，保留表结构，可加 `WHERE` 条件，效率最慢。 |

**11. UNION 与 UNION ALL 的区别？**

- **`UNION`**：合并结果集并**自动去重**，效率较低。
- **`UNION ALL`**：合并结果集，**不去重**，效率更高。

**12. count(1)、count(\*) 与 count(列名) 的区别？**

- **`COUNT(\*)`**：统计**所有行**（包括 `NULL` 行）。是 SQL 规范，MySQL 优化器会对其专门优化，通常是首选。
- **`COUNT(1)`**：与 `COUNT(*)` 效果基本相同，统计所有行。
- **`COUNT(列名)`**：统计指定列中**非 `NULL` 值**的行数。
- SQL 查询语句的执行顺序了解吗？

逻辑执行顺序：FROM -> ON -> JOIN -> WHERE -> GROUP BY -> HAVING -> SELECT -> DISTINCT -> ORDER BY -> LIMIT。

14. 介绍一下 MySQL 的常用命令（补充）

SHOW DATABASES;, USE db_name;, SHOW TABLES;, DESC table_name;, SELECT ..., INSERT ..., UPDATE ..., DELETE ..., EXPLAIN SELECT ...。

**15. MySQL bin 目录下的可执行文件了解吗（补充）**

- `mysql`：MySQL 客户端连接工具。
- `mysqld`：MySQL 服务器守护程序（核心服务）。
- `mysqldump`：数据库备份工具。
- `mysqladmin`：管理工具，如关闭服务器、查看状态。
- MySQL 第 3-10 条记录怎么查？（补充）

使用 LIMIT 子句：SELECT * FROM table_name LIMIT 2, 8;

- `2` 是起始偏移量（从 0 开始，即跳过前 2 条记录）。
- `8` 是要返回的行数（从第 3 条开始，返回 8 条，即第 3 到第 10 条）。
- 用过哪些 MySQL 函数？（补充）

聚合函数：COUNT(), SUM(), AVG(), MAX(), MIN()。

字符串函数：CONCAT(), SUBSTRING(), LENGTH(), UPPER(), LOWER()。

日期时间函数：NOW(), DATE_FORMAT(), DATEDIFF()。

18. 说说 SQL 的隐式数据类型转换？（补充）

当操作符两边的操作数数据类型不一致时，MySQL 会自动进行类型转换，以便操作能执行。例如，数字和字符串比较时，字符串可能会被转为数字。隐式转换可能导致索引失效（例如索引列是字符串，但查询时传入了数字，导致索引失效）。

19. 说说 SQL 的语法树解析？（补充）

SQL 语法树解析是 MySQL 执行查询的第一步。

1. **词法分析 (Lexer)**：将 SQL 语句分解成一个个的**词法单元 (Tokens)**。
2. **语法分析 (Parser)**：根据 SQL 语法规则，将 Tokens 组织成一个树形结构，即**抽象语法树 (AST)**。这个过程会检查 SQL 语句的语法是否正确。

## 数据库架构



20. 说说 MySQL 的基础架构？

MySQL 架构分为两层：

1. **Server 层**：包括连接器、查询缓存（8.0 移除）、**分析器**、**优化器**、**执行器**等，负责 SQL 语句的通用功能。
2. **存储引擎层**：负责数据的存储和提取，如 **InnoDB**、**MyISAM**。Server 层通过统一的接口与存储引擎进行通信。

**21. $\star$ 一条查询语句是如何执行的？**

1. **连接器**：验证用户身份、权限。
2. **查询缓存**：查询语句是否在缓存中（MySQL 8.0 默认关闭）。
3. **分析器**：进行词法分析和语法分析，生成 **抽象语法树**。
4. **优化器**：选择最佳的执行计划（如选择哪个索引、表连接顺序）。
5. **执行器**：调用存储引擎接口，根据执行计划获取数据。
6. **存储引擎**：从内存或磁盘中读取数据返回给执行器。
7. 一条更新语句是如何执行的？

更新语句（如 UPDATE）的执行流程：

1. Server 层执行流程与查询类似，分析、优化。
2. 执行器找到更新的记录，调用 InnoDB 接口。
3. InnoDB 将记录**读入内存**，修改值。
4. 同时，将更新操作写入 **redo log buffer**（并处于 `prepare` 状态）。
5. 将更新操作写入 **undo log**（用于回滚）。
6. Server 层写入 **binlog**。
7. InnoDB 将 redo log 状态置为 **`commit`**（**两阶段提交**完成）。
8. 事务提交成功，数据择机刷回磁盘。
9. 说说 MySQL 的段区页行（补充）

这是 InnoDB 存储结构：

- **行 (Row)**：最小的存储单元，一行记录。
- **页 (Page)**：是 InnoDB **磁盘管理最小单位**，默认 16KB，是数据和索引存储的基本单元。
- **区 (Extent)**：由 64 个连续的页组成，大小为 $64 \times 16KB = 1MB$。
- **段 (Segment)**：是区（Extent）的集合，分为数据段、索引段、回滚段等。

## 存储引擎



24. ⋆ MySQL 有哪些常见存储引擎？

最常见的是 InnoDB（支持事务，行级锁，外键）和 MyISAM（不支持事务，表级锁）。

25. 存储引擎应该怎么选择？

首选 InnoDB：适用于绝大多数场景，特别是需要事务支持、高并发和数据完整性的场景。

MyISAM：适用于只读、非事务性的简单应用或工具。

26. InnoDB 和 MyISAM 主要有什么区别？

| 特性 | InnoDB | MyISAM |

| :--- | :--- | :--- |

| 事务 | 支持 (ACID) | 不支持 |

| 锁级别 | 行级锁（并发高） | 表级锁（并发低） |

| 外键 | 支持 | 不支持 |

| 索引 | 聚簇索引（主键即数据） | 非聚簇索引 |

27. InnoDB 的 Buffer Pool了解吗？（补充）

Buffer Pool 是 InnoDB 存储引擎中最重要的内存区域，用于缓存数据页和索引页。所有对数据的读取和修改都是首先在 Buffer Pool 中进行的，以减少磁盘 I/O，提高性能。

## 日志



28. ⋆ MySQL 日志文件有哪些？

主要有四种：

1. **Redo Log**（重做日志）：InnoDB 独有，保证事务**持久性**，用于崩溃恢复。
2. **Undo Log**（回滚日志）：InnoDB 独有，保证事务**原子性**，用于事务回滚和 **MVCC**。
3. **Binlog**（二进制日志）：Server 层，用于**主从复制**和**时间点恢复**。
4. **Error Log**：记录服务器错误、启动、关闭等信息。
5. binlog 和 redo log 有什么区别？

| 特性 | Binlog (二进制日志) | Redo Log (重做日志) |

| :--- | :--- | :--- |

| 层级 | Server 层 (所有引擎) | InnoDB 引擎层 |

| 内容 | 逻辑操作（SQL 语句或行变化） | 物理操作（数据页修改） |

| 目的 | 复制、恢复 | 持久化、崩溃恢复 |

| 写入 | 追加写入 | 循环写入 |

30. ⋆ 为什么要两阶段提交呢？

两阶段提交 (2PC) 是为了保证 Redo Log 和 Binlog 在逻辑上的一致性。

- 如果没有 2PC，当 Redo Log 和 Binlog 只有一个写成功时，数据库重启后可能导致**主从数据不一致**（例如主库恢复数据但从库没收到 Binlog，或反之）。
- 2PC 通过将 Redo Log 分为 `prepare` 和 `commit` 两个阶段，保证了系统崩溃后，MySQL 能够根据日志状态，判断事务是否要最终提交，确保主从数据一致。

**31. $\star$ redo log 的写入过程了解吗？**

1. 事务执行过程中，产生 Redo Log 记录，先写入 **Redo Log Buffer**（内存）。
2. **Redo Log Buffer** 中的内容会根据不同的策略（`innodb_flush_log_at_trx_commit` 参数）择机写入到 **Redo Log File**（磁盘）。
   - `= 1`（最安全）：每次事务提交都刷盘。
   - `= 0`：每秒刷盘一次。
   - `= 2`：每次提交只写入 OS Cache，每秒 OS Cache 刷盘。

## SQL 优化



32. ⋆ 什么是慢 SQL？

慢 SQL 是指执行时间超过 long_query_time（默认 10 秒，生产环境通常设为 1 秒或更低）预设值的 SQL 语句。它们会被记录在慢查询日志中，是数据库性能瓶颈的主要来源。

**33. $\star$ 你知道哪些方法来优化 SQL？**

1. **索引优化**：创建合适的索引，遵循最左前缀原则，避免索引失效。
2. **分析和重写**：使用 `EXPLAIN` 分析执行计划，避免全表扫描 (`type=ALL`)，避免 `Using filesort` 和 `Using temporary`。
3. **查询语句优化**：只查询需要的列（不用 `SELECT *`），使用 `LIMIT`，将大查询拆分成小查询。
4. **架构优化**：分库分表，读写分离。
5. ⋆ explain 平常有用过吗？

用过。EXPLAIN 用于查看 SQL 语句的执行计划，是优化 SQL 的核心工具。

关注的关键字段：

- **`type`**（连接类型）：判断是否使用了索引，等级从优到劣：`const` > `eq_ref` > `ref` > `range` > `index` > `ALL`。
- **`key`**：实际使用的索引。
- **`rows`**：估计扫描的行数，越少越好。
- **`Extra`**：额外信息。关注 **`Using index`**（覆盖索引，优秀），避免 **`Using filesort`**（需要排序）和 **`Using temporary`**（需要临时表）。

## 索引



35. ⋆ 索引为什么能提高 MySQL 查询效率？

索引通过 B+树 结构，将随机 I/O 转化为顺序 I/O，帮助 MySQL 快速定位到数据记录的位置，从而减少磁盘 I/O 次数（避免全表扫描），极大地加快查询速度。

**36. $\star$ 能简单说一下索引的分类吗？**

1. **按数据结构**：B+树索引、Hash 索引、全文索引。
2. **按物理存储**：
   - **聚簇索引 (Clustered)**：数据和主键索引存储在一起（InnoDB）。
   - **非聚簇索引 (Secondary/Non-Clustered)**：索引和数据分离，索引叶子节点存储主键值（InnoDB 的普通索引）或行地址（MyISAM）。
3. **按逻辑功能**：主键索引、唯一索引、普通索引、联合索引。

**37. $\star$ 创建索引有哪些注意点？**

1. 在 **`WHERE`**、**`ORDER BY`**、**`GROUP BY`** 和 **`JOIN`** 的字段上创建索引。
2. 选择**区分度高**的列作为索引（重复值少的列）。
3. 使用**联合索引**代替多个单列索引，遵循**最左前缀原则**。
4. 避免对**更新频繁**的列创建过多索引（影响写性能）。
5. 考虑使用**覆盖索引**（`SELECT` 的列都包含在索引中）。

**38. $\star$ 索引哪些情况下会失效呢？**

1. 在索引列上使用了**函数**、**表达式**或进行了**计算**。
2. 使用 **`LIKE`** 进行模糊查询时，如果**通配符 (`%`) 放在开头**。
3. 使用了 **`OR`** 连接条件，但 **`OR`** 前后的列中有一个**没有索引**。
4. 对索引列进行了**隐式数据类型转换**。
5. 使用 **`!=`** 或 **`NOT IN`**。
6. MySQL 评估全表扫描比索引查找更快时（如数据量很小或查询结果集占比很大）。

**39. 索引不适合哪些场景呢？**

1. **数据量小**的表。
2. **更新频繁**的字段。
3. **数据重复度高**（区分度差）的字段，如性别字段。
4. 作为查询条件的字段，但**很少使用**。
5. 索引是不是建的越多越好？

不是。索引越多，写操作（INSERT/UPDATE/DELETE）的性能越差，因为每次写操作都需要维护所有的索引。同时，索引也会占用额外的磁盘空间。

**41. $\star$ 为什么 InnoDB 要使用 B+树作为索引？**

1. **磁盘 I/O 效率高**：B+树的节点（即页）大，能存储更多指针和索引键，树的**高度低**，减少了查询时的磁盘 I/O 次数。
2. **范围查询高效**：B+树的叶子节点之间通过**双向链表**连接，方便进行**范围查询**（只需找到起点，沿着链表遍历即可），而 B 树需要中序遍历。
3. **全表扫描性能高**：所有数据都集中在叶子节点，可以顺序扫描叶子链表。
4. ⋆ 一棵 B+树能存储多少条数据呢？

这是一个估算问题。

- 假设：页大小 $16KB$，主键 ID 为 `BIGINT` 8 字节，指针 $6$ 字节。

- **非叶子节点**（索引页）：可存储 $\approx 16KB / (8+6)B \approx 1170$ 个索引指针。

- **三层 B+树**：

  - 根节点：1 个页
  - 第二层：$1170$ 个页
  - 叶子层（数据页）：$1170 \times 1170 \approx 137$ 万个页。

- 每个叶子页存储约 16 条数据记录（假设行大小 1KB）。

- 总数据量： 137 万 ×16≈2200 万条记录。

  结论： 一棵高度为 3 的 B+树就能存储千万级别的数据。

- 索引为什么用 B+树不用普通二叉树？

普通二叉树在数据有序插入时会退化成链表，查找效率变为 O(N)。B+树作为多叉树，可以保持平衡，查找效率稳定在 O(loghN)（h 为树高），且树高非常低（通常 2-4 层）。

**44. $\star$ 为什么用 B+ 树而不用 B 树呢？**

1. **B+树只在叶子节点存储数据**，非叶子节点只存储索引键和指针，这使得非叶子节点能存储更多的索引，**降低树高**，减少磁盘 I/O。
2. **B+树的叶子节点通过链表连接**，非常利于数据库中的**范围查询**和**顺序扫描**。
3. B+树索引和 Hash 索引有什么区别？

| 特性 | B+树索引 | Hash 索引 |

| :--- | :--- | :--- |

| 结构 | 树形结构 | 哈希表结构 |

| 查询 | 等值、范围查询都支持 | 只支持等值查询（精确查找） |

| 排序 | 支持（索引有序） | 不支持（数据无序） |

| 索引失效 | 较少 | Hash 冲突时性能降低 |

| 适用引擎 | InnoDB（默认）、MyISAM | InnoDB 只有 自适应 Hash 索引 |

46. ⋆ 聚簇索引和非聚簇索引有什么区别？

| 特性 | 聚簇索引 (Clustered Index) | 非聚簇索引 (Secondary Index) |

| :--- | :--- | :--- |

| 存储 | 数据和索引存储在一起，叶子节点就是数据行。 | 索引和数据分离。叶子节点存储主键值（InnoDB）。 |

| 数量 | 一个表只能有一个（通常是主键）。 | 可以有多个。 |

| 查找 | 直接找到数据行，效率高。 | 需要回表（先找到主键，再通过主键查找数据行）。 |

47. ⋆ 回表了解吗？

回表是指通过非聚簇索引查找数据时，先根据索引找到对应的主键值，再使用这个主键值到聚簇索引中查找完整的用户数据行，这个第二次查找的过程就是回表。

48. ⋆ 联合索引了解吗？（补充）

联合索引（复合索引）是指在多个列上创建的索引。它遵循最左前缀原则，例如在 (a, b, c) 上创建索引，查询条件可以是 a，a, b，或 a, b, c。

49. ⋆ 覆盖索引了解吗？

覆盖索引是指查询的字段（SELECT 列表中的列）全部包含在所使用的索引中。

- 好处：**避免了回表**操作，大大减少了磁盘 I/O，提高了查询效率。
- 判断：`EXPLAIN` 结果的 `Extra` 字段中出现 **`Using index`**。
- ⋆ 什么是最左前缀原则？

最左前缀原则是指使用联合索引时，MySQL 会从索引的最左边的列开始匹配。

- 例如，索引是 `(a, b, c)`：
  - 查询条件包含 `a`、`a, b`、`a, b, c` 都可以使用索引。
  - 查询条件只有 `b` 或 `c, a` 等，则**无法**完全使用或使用不到索引。
- ⋆ 什么是索引下推？

索引下推 (Index Condition Pushdown, ICP) 是 MySQL 5.6 引入的优化技术。

- 它允许 MySQL 在**存储引擎层**利用索引中的列进行过滤，**减少回表次数**。
- **例如：** 索引 `(name, age)`，查询 `WHERE name = 'A' AND age > 20`。
  - **无 ICP：** 找到所有 `name = 'A'` 的主键，**回表**到 Server 层再判断 `age > 20`。
  - **有 ICP：** 在存储引擎层就利用索引中的 `age` 判断 `age > 20`，只将符合条件的记录**推给** Server 层，减少了回表次数。
- 如何查看是否用到了索引？（补充）

使用 EXPLAIN 命令查看 SQL 语句的执行计划，重点关注 type（连接类型）和 key（实际使用的索引）字段。

## 锁



**53. $\star$ MySQL 中有哪几种锁？**

1. **按粒度**：**全局锁**、**表级锁**（表锁、元数据锁 MDL）、**行级锁**（Record Lock, Gap Lock, Next-Key Lock）。
2. **按性质**：**共享锁 (S Lock)**（读锁）、**排他锁 (X Lock)**（写锁）。
3. **按乐观/悲观**：**乐观锁**（版本号/CAS）、**悲观锁**（数据库锁机制）。
4. 全局锁了解吗？（补充）

全局锁是对整个数据库实例加锁。执行 FLUSH TABLES WITH READ LOCK (FTWRL) 命令时产生。

- 作用：让整个库处于**只读状态**。常用于**逻辑备份**，确保备份数据的一致性。
- ⋆ 说说 MySQL 的行锁？

行锁是 MySQL InnoDB 引擎独有的，用于锁定表中的某一行或某几行数据，粒度最小，并发度最高。

- **共享锁 (S Lock)**：允许其他事务继续加 S 锁，但不能加 X 锁。
- **排他锁 (X Lock)**：不允许其他事务再加 S 锁或 X 锁，实现独占写入。
- 临键锁了解吗？

临键锁 (Next-Key Lock) 是 InnoDB 在可重复读 (RR) 隔离级别下实现的。它是 行锁 (Record Lock) 和 间隙锁 (Gap Lock) 的组合。

- **行锁**：锁定当前记录。
- **间隙锁**：锁定记录前后的**间隙**，防止新的记录插入，从而**解决幻读问题**。
- 意向锁是什么知道吗？

意向锁 (Intention Lock) 是一种表级锁，用于表明事务稍后会对表中的某行加锁（S 或 X）。

- **意向共享锁 (IS Lock)**：表示事务打算给数据行加 **S 锁**。
- **意向排他锁 (IX Lock)**：表示事务打算给数据行加 **X 锁**。
- 作用：提高效率。当一个事务想要给**表加锁**时，不需要遍历所有行来判断是否有行锁，只需要检查表上的**意向锁**即可。

**58. $\star$ MySQL 的乐观锁和悲观锁了解吗？**

- **悲观锁**：认为并发冲突**总是发生**，因此在操作数据前**先加锁**（如数据库的行锁、表锁），保证操作的独占性。
- **乐观锁**：认为并发冲突**很少发生**，不加锁，而是在更新时检查数据是否被其他事务修改过（通常通过添加 **`version` 版本号**或**时间戳**字段实现）。
- 遇到过 MySQL 死锁问题吗，你是如何解决的？

死锁是两个或多个事务在相互等待对方释放锁资源，导致都无法继续执行。

解决思路：

1. **定位**：使用 `SHOW ENGINE INNODB STATUS` 查看 LATEST DETECTED DEADLOCK 信息。
2. **预防**：
   - **以相同顺序**访问资源（表/行）。
   - **批量操作**：将大事务分解成小事务。
   - **索引优化**：确保 SQL 走索引，减少锁的范围（表锁退化）。
   - 使用较低的**隔离级别**（如 RC）。

## 事务



60. ⋆ MySQL 事务的四大特性说一下？

事务的四大特性，简称 ACID：

1. **原子性 (Atomicity)**：事务是最小的执行单位，要么**全部成功**，要么**全部失败回滚**。
2. **一致性 (Consistency)**：事务完成后，数据库必须保持**一致状态**（从一个有效状态转移到另一个有效状态）。
3. **隔离性 (Isolation)**：多个事务并发执行时，事务内部的操作应**互不干扰**。
4. **持久性 (Durability)**：事务提交后，对数据的修改是**永久的**，即使系统崩溃也不会丢失。

**61. ACID 靠什么保证的呢？**

- **原子性 (A)**：主要通过 **Undo Log**（回滚日志）实现。
- **持久性 (D)**：主要通过 **Redo Log**（重做日志）实现。
- **隔离性 (I)**：主要通过**锁机制**和 **MVCC**（多版本并发控制）实现。
- **一致性 (C)**：由前三者共同保证，并且需要**应用程序的逻辑**来确保业务数据满足约束。
- ⋆ 事务的隔离级别有哪些？

SQL 标准定义了四种隔离级别，从低到高：

1. **Read Uncommitted (RU)**：读未提交。可能出现**脏读**。
2. **Read Committed (RC)**：读已提交。避免了脏读，可能出现**不可重复读**和**幻读**。
3. **Repeatable Read (RR)**：可重复读。（**MySQL InnoDB 默认**）。避免了脏读和不可重复读，但**理论上**仍有幻读，MySQL 通过 **临键锁** 避免了**大部分**幻读。
4. **Serializable (S)**：串行化。最高级别，彻底避免并发问题，但**性能最差**（强制事务串行执行）。
5. 事务的隔离级别是如何实现的？

主要依赖于：

- **锁机制**：用于隔离写操作。
- **MVCC (多版本并发控制)**：用于解决读写冲突，让读操作不阻塞写操作。RC 和 RR 级别主要依赖 MVCC 实现。
- ⋆ 请详细说说幻读呢？

幻读 (Phantom Read) 是指一个事务在同一查询条件下，两次查询的结果集行数不同。

- 第一次查询：`SELECT COUNT(*) FROM T WHERE id > 10;` 结果 10 行。

- 另一个事务：`INSERT INTO T (id, ...) VALUES (11, ...);` 并提交。

- 当前事务第二次查询：SELECT COUNT(*) FROM T WHERE id > 10; 结果 11 行。

  解决：MySQL InnoDB 在 RR 级别主要通过 临键锁 (Next-Key Lock) 机制来锁定查询范围，阻止新数据的插入（Gap Lock），从而避免了幻读。

- ⋆ MVCC 了解吗？

MVCC (Multi-Version Concurrency Control)，多版本并发控制，是 InnoDB 解决读写冲突的机制。

- **核心思想**：通过保存数据的**多个版本**，实现读操作可以读到旧版本数据，而不用等待写锁释放。
- **主要组成**：
  - **隐式字段**：每行记录都包含 **`trx_id`** (最后修改的事务 ID) 和 **`roll_pointer`** (指向 Undo Log 的指针)。
  - **Undo Log**：存储了数据的历史版本。
  - **Read View**：事务开启时创建，记录当前活跃的事务 ID 列表，用于判断当前事务能看到哪个版本的数据。

## 高可用



66. MySQL 数据库读写分离了解吗？

读写分离是将数据库的读操作分配到从库 (Slave)，将写操作分配到主库 (Master)。

- **目的**：减轻主库的压力，提高数据库的并发处理能力。

**67. 读写分离的实现方式有哪些？**

1. **代码层面**：在应用程序代码中判断 SQL 类型（`SELECT` 还是 `INSERT/UPDATE/DELETE`），手动路由到主库或从库。
2. **中间件层面**：使用如 **Mycat, ShardingSphere** 等数据库中间件，它们负责解析 SQL 并自动路由。
3. 主从复制原理了解吗？

MySQL 主从复制基于 Binlog 实现，主要有三个线程：

1. **Binlog Dump 线程 (Master)**：主库将 Binlog 发送给从库。
2. **I/O 线程 (Slave)**：从库接收 Binlog 内容，并写入自己的 **Relay Log**（中继日志）。
3. **SQL 线程 (Slave)**：从库读取 Relay Log 中的事件，并在从库上**重放执行**，从而保持主从数据同步。

**69. 主从同步延迟怎么处理？**

1. **优化 SQL**：避免在从库执行耗时过长的慢 SQL，导致 SQL 线程堵塞。
2. **配置优化**：开启 **并行复制 (Parallel Replication)**，让从库多个线程并发执行 Relay Log 中的事件。
3. **硬件升级**：提升从库的配置（尤其是 I/O 性能）。
4. **业务处理**：对于对数据一致性要求高的业务，从库查询后可**强制读主库**。
5. ⋆ 你们一般是怎么分库的呢？

分库是将数据分散到不同的数据库实例（甚至不同的服务器）中，以突破单机存储容量和连接数瓶颈。

- **垂直分库**：按**业务功能**拆分，例如将用户中心库、订单库、商品库分开。
- **水平分库**：按**某种规则**（如用户 ID 取模、时间范围）将一张大表的数据分散到**多个数据库**的同名表中。
- ⋆ 那你们是怎么分表的？

分表是将一张表的数据分散到同一个数据库实例的多张表中。

- **垂直分表**：按**字段**拆分，将一个有很多列的大表，拆分成几个小表，提高查询效率（因为行变小了）。
- **水平分表**：按**某种规则**将一张大表的数据分散到**同一数据库**的多个结构相同的表中（如 `user_001`, `user_002`），以突破单表数据量瓶颈。

**72. 水平分库分表的分片策略有哪几种？**

1. **哈希/取模分片**：根据分片键（如用户 ID）取模，均匀分散到不同的库/表。
2. **范围分片**：按时间或 ID 范围划分，例如 2024 年的数据在一个库，2025 年的在另一个库。
3. **时间分片**：按日期（如月、年）分表，方便历史数据归档。
4. **一致性哈希**：用于解决节点扩容时数据迁移量大的问题。
5. 不停机扩容怎么实现？

不停机扩容通常指在水平分库分表后增加分片节点：

1. **双写**：在新旧分片规则下**同时写入**数据。
2. **数据迁移**：后台任务将旧分片中的历史数据迁移到新分片。
3. **校验**：校验新旧数据的一致性。
4. **切换读写**：将流量（读写）**原子性**地切换到新的分片规则。

**74. 常用的分库分表中间件有哪些？**

- **ShardingSphere**（原 Sharding-JDBC 和 Mycat 的结合体，Apache 顶级项目）。
- **Mycat**（基于阿里 Cobar 开源的分布式数据库中间件）。
- **Vitess**（YouTube 开源，专为大规模分片设计）。

**75. 你觉得分库分表会带来什么问题呢？**

1. **事务问题**：跨库事务难以保证 ACID 特性（需要使用分布式事务，如 XA 或 TCC）。
2. **跨库 Join**：原来简单的 JOIN 操作变为复杂的跨库联表查询，效率低。
3. **全局主键**：需要单独设计全局唯一 ID 生成策略（如雪花算法）。
4. **数据迁移和扩容**：运维复杂度高。
5. **SQL 限制**：部分复杂的 SQL 语句可能不支持。

## 运维



76. 百万级别以上的数据如何删除？

直接使用 DELETE 语句会导致锁表和大量 Redo Log 产生，影响性能。

推荐方案：

1. **分批删除**：使用循环和 `LIMIT` 语句，每次删除少量数据（例如 1000-5000 行），在每次删除后 `COMMIT`，减小事务锁的持有时间。
2. **TRUNCATE PARTITION**：如果使用了分区表，可以直接 `TRUNCATE` 掉某个分区。
3. 千万级大表如何添加字段？

在 MySQL 5.6 之前，ALTER TABLE 是锁表操作。

推荐方案（高版本 MySQL）：

1. **使用 `ALGORITHM=INPLACE, LOCK=NONE`**：MySQL 5.6+ 支持 **在线 DDL**，可以在不阻塞 DML（数据操作）的情况下进行大部分 `ALTER TABLE` 操作。
2. **工具辅助**：使用 **Percona 的 `pt-osc`** 或 **GitHub 的 `gh-ost`** 工具，这些工具通过创建影子表、触发器同步数据来实现**零停机 DDL**。
3. MySQL 导致 cpu 飙升的话？

CPU 飙升通常是Server 层的复杂计算导致的。

排查步骤：

1. **查看状态**：使用 `SHOW PROCESSLIST` 或 `sys.processlist` 查找是否有大量**慢查询**或处于 **`Running`** 状态的 SQL。
2. **慢 SQL 定位**：检查慢查询日志，找出耗时长的 SQL。
3. **执行计划分析**：对慢 SQL 使用 `EXPLAIN`，检查是否存在**全表扫描**、**`Using filesort`**、**`Using temporary`** 等导致 CPU 密集计算的操作。
4. **连接数**：检查连接数是否过多（`max_connections`），导致 CPU 消耗在线程创建和销毁上。
5. **优化**：针对性地**创建索引**或**重写 SQL**，避免不必要的排序和临时表。
